# Design selection

This is the advisor's review of the three concepts after the owner ruled that pickglass must be an independent tool that attaches to a running BEAM node, as observer and Observer Web do. It selects the Opus concept, adapted to attach over distribution with a pushed, dependency-free agent. `plan.md` turns it into work packages.


Research facts I checked before judging (all in `docs/research/`): observer executes `observer_backend` from `runtime_tools` on the target and spawns its collectors there with `spawn_link(Node, ...)` (`research-beam-inspectors.md` 126-133); Observer Web goes through `:rpc.call` into stdlib and runtime_tools functions, and its Metrics page needs Observer Web's own module on each node (line 61); LiveDashboard pushes its own module with `:code.load_binary` when the target lacks it (line 193); observer_cli's CLI refuses to inject code, while its TUI auto-loads bytecode through recon and documents that as a riskier mode (157-163). On the runtime side: a trace session is destroyed when its sole strong-handle holder dies, before the `DOWN` is delivered, and survives if the handle was copied to any long-lived process (`research-beam-runtime-apis.md` 60-68); `erpc` runs each call in a temporary process on the target, so a session created inside one dies when the call returns (317); and a hidden sidecar ran `os:cmd` on the target, so distribution is full mutual trust (311). The owner's attach design (hidden node, pushed long-lived agent, teardown on disconnect) is therefore the same shape LiveDashboard and observer_cli's TUI already use, and it is the only shape that can own a probe from outside the node.

## Concept sonnet: in-node host, capture-first

What it is. The whole inspector is a library linked into the target VM: collectors, a probe supervisor, an observation hub with client leases, a capture store, an audit ring, and the Lustre web component, all running inside the daemon being measured. The thesis is that everything reads one thing, a versioned append-only NDJSON capture, so the live page is "a capture still being appended to", comparison is a function over two captures, and the offline `pickglass view` release can open a capture from a machine with no host. Its second structural rule is authority as a type: collectors accept only an opaque `Authorized(Command)` that a pure `policy` package alone can construct, so a forged Lustre event or a direct HTTP request that skips the gateway cannot compile into a collector call.

Deployment and UI. Loom adds a `[daemon] diagnostics` switch, mounts the pickglass component behind its existing `ui_http`/`ui_socket` ticket, origin, cookie, nonce and CSP machinery, and maps its page credential to a pickglass `Principal`; a non-Loom host mounts it behind a minimal loopback listener pickglass supplies. The static release is explicitly an offline tool (`view`, `export`, `compare`, `doctor`) with no collectors and no distribution port; attach mode is excluded from v1-v3 and, if ever added, is observation-only. The UI is one `<pickglass-app>` server component per tab, server-rendered SVG capped at 2,000 rects with one click handler that hit-tests server-side, view workers computing `ViewModel`s off the Lustre process, a columnar `BitArray` store for large captures, and a two-step plan/confirm dialog for every probe that shows scope, cost and perturbation before the operator commits.

Against the owner's goals. Its strengths are the sharpest authority design of the three (opaque `Authorized`, exhaustive `required_capabilities` so an undecided command fails the build, plan/confirm with digest and fingerprint revalidation, denied attempts audited), the best data model for #720's measurement rules (`Cell = Value | Absent(reason)`, `Additivity = Additive | Overlapping(why)` so group-by refuses to total binary references, rates from adjacent monotonic instants), a supervision tree from `process_info(parent)` that needs no blocking `which_children` and finds Loom's non-application root, and a Compare page that allows a verdict per column. Its weakness is fatal under the new direction: it is exactly the thing the owner ruled out, a library the host embeds and a UI mounted inside the host's web server, with the capture store, analysis and Lustre runtimes living in the heap whose growth is the question. The viewer and the policy, core and export packages survive the attach requirement; the host, hub and web-mount packaging do not.

## Concept opus: a small agent, a separate viewer, a typed wire

What it is. Two programs. A small `pickglass_agent` library inside the target VM is the only code that touches the runtime, holds trace sessions, enforces budgets and per-connection grants, and keeps a pin table of monitored targets. A separate viewer OS process (the static release) does everything else: Lustre UI, capture storage, analysis and layout, comparison, exports, and OS-level readings of RSS, CPU and start identity for any OS pid the agent names. The thesis is that the inspector's footprint in the target must be a handful of processes with fixed budgets reported as their own owner, and that "the wire is the capture": every agent reply is a self-describing record with timestamps, units, method, coverage and truncation, and a capture file is those records as received, so a view cannot show what a saved capture lacks.

Deployment and UI. The agent is a hex dependency the host starts under its own supervision tree (`loomd --inspect`, which also adds `+Muatags true`), listening on an owner-only unix socket with a 256-bit token and a discovery descriptor; it rejects Erlang distribution for the normal path on three grounds (full-trust cookie, `erpc` temporary processes cannot own sessions, census-then-truncate across the boundary) and keeps a "bare attach" distribution mode only as an observation-only fallback labelled full trust in the UI. The viewer serves on `127.0.0.1` with a random port, single-use ticket links, `HttpOnly`/`SameSite=Strict` cookie, per-page nonce and a strict CSP; pages are server-rendered SVG with layout pruned to a few thousand elements, analysis in weft tasks with deadlines, keyed paged tables, and one agent link per agent that coalesces identical requests across tabs. Probes are a `weft/state_machine` controller holding the strong handle, with a separate linked tracer holding only the weak handle so a flooded mailbox cannot delay the controller's deadline or cancel.

Against the owner's goals. This is the closest to the attach requirement in process topology: UI, captures, analysis and layout already live in pickglass's own VM, the agent is already small and budget-bounded with per-connection grants, targets are already named by monitor-backed pin tokens that a restart invalidates (which a remote viewer needs, because its view of pids is always stale), and the OS readers already run outside the target. The `Request` type is closed, `ProbeSpec` resolves modules with existing-atom semantics, and the lifecycle table handles owner disconnect explicitly. Its weaknesses: the agent is still a library the host must depend on and be rebuilt with, the transport decision is argued the opposite way from the owner's ruling, the ownership `Provider` is a record of Gleam closures registered at agent start (impossible for a pushed agent), the agent uses weft and gleam_otp (impossible for a pushed, dependency-free agent), and the probe start is one step rather than sonnet's plan/confirm.

## Concept fable: three roles, one codebase, embedded first

What it is. A capture-first inspector whose collector is an OTP application (`pickglass_probe`) the host embeds, with the `Capture` value as the single structure that live pages, the offline viewer, exports and comparison all read through pure `core` code; a live page is "the newest capture plus a bounded ring of older ones", never a separate live model. The same code plays three roles: embedded (primary, closes #720), attach (the static release as a hidden node over Loom's existing `--profile` node, observation-only, labelled full trust on screen), and viewer (files only). Its stated reason for embedding is the ownership rule: the strong handle, the `scheduler_wall_time` refcount, timers and label reads must all be owned by a long-lived target process, and `erpc` cannot provide one.

Deployment and UI. `loomd --inspect` starts the application and mounts the pages under Loom's `/ui` listener through a protocol-change; `pickglass attach` reuses `observer.sh`'s node discovery and private `HOME` cookie path, starts with `-hidden -dist_listen false`, and runs only observation collectors over `erpc`; `pickglass attach --once --out cut.pgcap` replaces `loom-profile` on day one. Ownership enters through three generic extension points registered at `probe.start`: a `label` with a fixed tagged tuple `{pickglass_owner, 1, Scope, Role}` read with `process_info(P, label)`, an `OwnerProvider` and `RoleProvider` called once per generation in their own deadline tasks, and a phase-3 `SummaryProvider` the host implements. Pages are one server component each, subscribing to the coalesced census ring at `init` (no page ever requests a census), server-rendered SVG with a 1/2,000-width box cutoff and 24 literal colour classes, keyed and memoized `<g>` per frame, and a capability banner on every page naming the role and the data-source line.

Against the owner's goals. Its strengths are the cleanest attribution model (attribution carries `source` and `confidence`, the join prefers Label over Registry over Supervision and shows disagreement), a label format that is a wire convention rather than a library call, `core/authority.decide` as a pure total table with the principal read only from the socket's admission record, the explicit "a read-only label on a full-trust channel would be a lie" banner, and the smallest and most honest probe table (a flame graph is refused for a counters source). Its weakness is the same as sonnet's: the primary role is an embedded OTP application with the UI mounted in the host, so the daemon must be rebuilt with pickglass and the capture ring and Lustre runtimes sit in the measured heap. Its attach role is the right starting point but is observation-only by design and so cannot deliver the must-have probe views (flame, DAG, timeline) against an unmodified target; the design has no way to run a probe without the host embedding `pickglass_probe`.

## Selection

Build on opus. It is the only concept whose process topology already matches the owner's ruling: the UI, capture store, analysis workers, layout, exports and OS readers live in pickglass's own VM, the target-side footprint is a small agent with fixed budgets, every request is a closed typed record, targets are named by monitor-backed pin tokens, and the probe controller/tracer split and lifecycle table are the most complete of the three. The work is to change how the agent gets there and what it is made of, not to redesign the product around it.

Three things change to satisfy attach. First, transport and delivery: the viewer joins as a hidden node (`-hidden -dist_listen false`, loopback interface, cookie read from an owner-only file path, never argv or environment, exactly as `observer.sh` does; for Loom the existing `loomd --profile` node and `<state-root>/tokens/` directory are the target and `+Muatags` comes for free), checks the target's OTP version and that no `pickglass_agent@*` module is already loaded, pushes the agent's modules with `code:load_binary`, spawns one long-lived registered agent process that owns the pin table, every trace session, the `scheduler_wall_time` refcount and the audit ring, and monitors the viewer's link process; on `nodedown`, viewer death or explicit detach the agent destroys every session, releases every flag, exits, and the last step purges and deletes its own modules. Opus's unix-socket listener, token, descriptor file, `--inspect` flag and "bare attach" mode all go; the agent's existing per-connection grant checks become per-attach grant checks, and the stateless observation calls (`memory`, `statistics`, `system_info`, `instrument`) may still go through `erpc` directly. Second, the agent becomes a zero-dependency package: its modules live under `agent/src/pickglass_agent/` so they compile to `pickglass_agent@*` names, it imports nothing (no `gleam_stdlib`, `gleam_erlang`, `gleam_otp` or weft, because pushing any of those would replace the target's own copies and a purge kills processes running the old code), and it is held to that by a lint rule plus an xref check over its generated beams. This is the one place the weft rule cannot apply; the honest answer is to keep the agent small enough (one receive loop, the probe controller and tracer, the census worker) that its hand-rolled machinery is a few hundred lines with a written exemption, and to put every weft-shaped thing (agent link, coalescer, analysis pool, deadline tasks) in the viewer where weft is available. Third, the ownership extension point becomes a protocol instead of a registered closure: fable's label tuple `{pickglass_owner, 1, Scope, Role}` set by the host with `proc_lib:set_label` and decoded generically by the agent, an optional conventionally registered host provider process answering a closed message set (OS children with roles, workload facts, supervision roots) with a deadline, and opus's `MeasureYourself(budget, reply_to)` self-measure message for summaries, with the summary kinds a process supports advertised in its label. Loom then needs no pickglass dependency at all: it labels its session, strand, worker, keeper, manager and gateway processes, optionally registers the provider process and teaches the keeper the self-measure message, each as plain Loom code under a `protocol-change/NNN.md` that freezes the tuple shapes.

Take from sonnet: the `policy` package with opaque `Authorized(Command)` and exhaustive `required_capabilities`, the plan/confirm two-step for every probe and targeted GC (the plan carries scope, matched-function count from the agent, estimated cost, perturbation class and a digest; confirm is refused unless the same principal confirms an unexpired, unchanged plan), the `Cell`/`Additivity` model so `Overlapping` columns refuse totals, the `parent`-based supervision walk as the default with `which_children` as an on-demand supplement, the observer-effect duty-cycle meter, and the per-column verdict in Compare. Take from fable: the attribution record with `source` and `confidence` and the Label > Registry > Supervision join, the capability banner on every page, `pickglass attach --once --out` as the `loom-profile` replacement that ships in the first milestone, and the "flame graph refused for a counters source" rule. Keep opus's capture format (gzip NDJSON with header, clock, coverage, perturbation, audit and footer records) with sonnet's rule that an unterminated file renders as `Partial(NoFooter)`.

On full mutual trust: it is acceptable for a localhost owner tool, because the OS user who can read the 0600 cookie file already has every power the cookie grants (kill the daemon, attach a debugger, read its memory), and because `loomd observer` already runs with this posture. The conditions are that the viewer is the only holder of the cookie and never writes it to HTML, logs, exports or captures (grep fixtures), the viewer accepts no inbound distribution (`-dist_listen false`) so no third node can transit through it, the target's listener stays loopback-bound, jailed session tools and satellites keep `tokens/` masked so Rule Zero holds, and the pushed agent is namespaced, version-checked and unloaded on detach. What the server-side authority model must still do, and why it cannot be delegated to the agent: a compromised viewer VM holds the cookie, so the agent's closed protocol defends against bugs (a forged Lustre event can only become a typed `Command`), not against a hostile viewer. The gate that matters is therefore in the viewer, between the browser and the agent link: principal established once at socket admission and never read from an event, every command through `policy.authorize` producing the opaque `Authorized` value before it can reach the link, plan/confirm for probes, audit of every allow and deny, pins as the only way to name a target, and the forged-event, direct-request and stale-pin fixtures #720 asks for. The agent enforces budgets, admission and pin validity a second time as defense in depth. Remote access later is TLS and multi-user authentication at the viewer's front door with a per-principal grant set, as opus §6.5 describes; the viewer remains a fully trusted administrative component and that should be written down now.

Top three risks to retire first, in order:

1. The pushed zero-dependency agent. Prove on a real `loomd --profile` daemon that a Gleam package with no imports compiles to beams whose xref shows no `gleam@*`/`gleam_stdlib` calls, loads over `erpc` with `code:load_binary`, runs a registered process that owns a trace session across many viewer requests, and on `kill -9` of the viewer destroys the session (checked with `trace:session_info(all)`), releases `scheduler_wall_time`, and purges its own modules without killing any target process. Also confirm `instrument`/`runtime_tools` is in Loom's release closure (fable notes it was missing in the September investigation) and whether `process_info(P, label)` is readable from the agent for closure-spawned weft actors.
2. Probe lifecycle over distribution. Run #720's phase-4 matrix (cancel, deadline, disconnect, target death and restart, tracer crash, agent kill, daemon shutdown, concurrent `dbg` user, hot reload, event storm) with the controller on the target and the owner on another node, and confirm the pin-token invalidation on `DOWN` refuses a stale target. This is where the "lost delivery turns a finite probe into an indefinite profiler" failure would live.
3. Cost and responsiveness measured end to end. Census cost at 50k-100k processes with the bounded top-K result crossing the node boundary (never the whole list), `+Muatags` overhead on Loom's normal workload, and Lustre render/diff cost for a 3,000-element SVG in the viewer under four tabs; these decide the default cadence, whether `--profile`'s allocator tagging stays the default attach target, and whether a canvas client component ever enters scope. Alongside this, land the Loom label protocol-change early, because every ownership view shows `unknown` until Loom labels its processes, and that is the first useful answer to #720.
